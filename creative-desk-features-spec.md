# Creative Desk v2 — спецификация новых функций

> Документ для исполнителя-разработчика (Claude Code). Описывает, **что** добавить в существующий сервис Creative Desk (репозиторий `Takaesi/Creative-Desk`), **как это должно работать** и **как проверить, что сделано правильно**. Если что-то в документе противоречит здравому смыслу или существующему коду — остановись и задай вопрос, а не угадывай.

## 0. Как работать с этим документом

### 0.1. Контекст продукта

Creative Desk — сервис управления креативным отделом медиабаинговой команды. Сейчас это трекер задач «байер → креативщик»: канбан, учёт времени, AI-расходы, аналитика руководителя, история действий.

**Цель версии 2:** превратить трекер задач в систему, которая знает, **какие креативы приносят деньги**. Замкнуть цикл:

```
ТЗ → креатив → приёмка → запуск в рекламу → результаты (CTR/ROI) → вердикт → вариации победителя → новое ТЗ
```

Сейчас цикл обрывается на статусе «Готово»: что стало с креативом дальше, сервис не знает.

### 0.2. Обязательные правила реализации

1. **Не ломать существующее.** Все текущие функции (канбан, переходы статусов, учёт времени, AI-расходы, аналитика, история, роли, демо-вход) должны продолжить работать. Существующий smoke-тест (`npm test`) должен проходить.
2. **Стек не менять.** Backend: Node.js 20 + Express + SQLite (`better-sqlite3`). Frontend: React 18 + Vite + React Router + lucide-react, стили — CSS custom properties вручную. **Новые тяжёлые зависимости не добавлять** (никаких UI-китов, ORM, библиотек графиков). Графики — на HTML/CSS/inline SVG, как в текущей аналитике. Допустимо добавить только мелкие библиотеки, если без них никак (например, парсер CSV можно написать самому — формат простой).
3. **Миграции идемпотентны.** Новые таблицы — `CREATE TABLE IF NOT EXISTS`, новые колонки — через проверку `PRAGMA table_info` (как уже сделано в `server/db.js` для `first_submitted_at`). База, созданная старой версией, должна обновляться без потери данных.
4. **Бизнес-правила — в одном месте.** Права на действия расширяются в `allowedActions()` (`server/domain.js`) и для задач, и по аналогии — в новой функции `allowedCreativeActions(creative, user)` для креативов. Сервер проверяет права, клиент по этому же списку решает, какие кнопки показывать.
5. **Всё пишется в историю.** Каждое изменяющее действие (создание, смена статуса, вердикт, ввод метрик, импорт, пин, изменение справочника) — запись в `history` через `logHistory()` в той же транзакции, что и само действие. Для действий над креативами добавить в `history` колонку `creative_id` (nullable).
6. **Интерфейс — на русском**, как сейчас. Даты — в локальном времени пользователя, деньги — в рублях с разделителем тысяч (`12 500 ₽`), проценты — с одним знаком после запятой.
7. **Демо-данные обязательны.** Каждая новая функция должна быть видна сразу после входа под демо-пользователем: `server/seed.js` расширяется так, чтобы новые разделы не были пустыми (см. раздел 5).
8. **Тесты.** Для каждой функции P0 и P1 добавить проверки в `server/smoke-test.js` (сценарии указаны в критериях приёмки).
9. **Работай по фазам** (раздел 0.4). После каждой фазы: `npm test` зелёный, `npm run build` проходит, приложение запускается, коммит с понятным сообщением.

### 0.3. Глоссарий

| Термин | Значение |
|---|---|
| **Задача (task)** | ТЗ от байера на изготовление креативов. Уже существует. |
| **Сдача (submission)** | Отправка результата на проверку. Каждая сдача — раунд: 0 — первая, 1..N — после правок. Уже существует. |
| **Креатив (creative)** | **Новая сущность.** Один конкретный рекламный материал (файл или ссылка) из сдачи. У задачи на «5 баннеров» будет 5 креативов. Живёт дольше задачи: тестируется, получает метрики, вердикт, может выгореть, порождает вариации. |
| **Версия креатива** | Номер раунда сдачи + 1. После правок появляется новая версия того же креатива. |
| **Код креатива** | Уникальный короткий код `CD-<id>` (например `CD-142`). Байер вставляет его в название объявления в рекламном кабинете или трекере, чтобы потом сопоставить статистику. |
| **Оффер** | Продукт/предложение, которое рекламируется. Сейчас — текстовое поле задачи, станет справочником. |
| **Подход (approach)** | Креативная гипотеза / угол подачи: «Боль», «Отзыв», «До/после», «Новость», «Эксперт», «Дефицит» и т. п. **Новый справочник.** |
| **Метрики** | Показы, клики, конверсии, расход, доход за конкретный день по конкретному креативу. Из них считаются CTR, CR, CPA, ROI. |
| **Вердикт** | Итог теста креатива: победитель / средний / не зашёл. |
| **Выгорание** | Падение эффективности креатива-победителя со временем (аудитория устала). Определяется по падению CTR. |
| **Вариации** | Новые креативы, сделанные на основе победителя (тот же подход, другой визуал/хук). |
| **Единицы трудоёмкости (units)** | Условная оценка объёма задачи для планирования загрузки. |
| **WIP-лимит** | Максимум задач, которые креативщик может одновременно держать в работе. |

## 1. Роли и права (сводная матрица)

Роли остаются прежними: `buyer` (байер), `creative` (креативщик), `lead` (руководитель). Ниже — права только на **новые** действия. «Свои» для байера = задачи/креативы, где `buyer_id` = он.

| Действие | Байер | Креативщик | Руководитель |
|---|---|---|---|
| Смотреть Библиотеку креативов | все креативы | все креативы | все |
| Вносить/импортировать метрики | свои креативы | — | все |
| Ставить и менять вердикт, отмечать «Запущен», «Выгорел», «В архив» | свои | — | все |
| «Сделать вариации» | свои креативы (новая задача создаётся от его имени) | — | все (байер новой задачи = байер исходной) |
| Ставить пины-замечания на креатив | свои, пока задача на проверке | — | все, пока задача на проверке |
| Отмечать пин исправленным | — | если он исполнитель задачи | все |
| Шаблоны ТЗ | создавать личные, пользоваться личными и общими | — | всё, включая общие |
| Справочники (офферы, подходы, AI-сервисы с ценами), пользователи (ставка, мощность, WIP), пороги | смотреть офферы и подходы | смотреть офферы и подходы | полное редактирование |
| Страница «Загрузка команды» | смотреть | смотреть | смотреть + назначать |
| Себестоимость креативов в рублях | своих задач | — (видит только свои часы и кредиты) | все |
| Подключить Telegram | да | да | да |

## 2. Изменения модели данных

Все изменения — в `server/db.js`. Колонки, отмеченные **(миграция)**, добавляются к существующим таблицам через проверку `PRAGMA table_info`.

### 2.1. Справочники и настройки

```sql
CREATE TABLE IF NOT EXISTS offers (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  name       TEXT NOT NULL UNIQUE,
  vertical   TEXT NOT NULL DEFAULT '',          -- нутра, гемблинг, финансы, e-com и т.п.
  is_active  INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS approaches (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  name        TEXT NOT NULL UNIQUE,              -- «Боль», «Отзыв», «До/после»...
  description TEXT NOT NULL DEFAULT '',
  is_active   INTEGER NOT NULL DEFAULT 1,
  created_at  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS ai_services (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  name             TEXT NOT NULL UNIQUE,
  credit_price_rub REAL NOT NULL DEFAULT 0 CHECK (credit_price_rub >= 0),
  is_active        INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE IF NOT EXISTS settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

Ключи `settings` и значения по умолчанию (создать при старте, если нет):

| key | По умолчанию | Смысл |
|---|---|---|
| `wip_limit_default` | `3` | WIP-лимит, если у пользователя не задан свой |
| `verdict_min_spend` | `50` | Минимальный суммарный расход (₽ или $ — единица одна на весь сервис, см. `currency`), после которого система предлагает вердикт |
| `verdict_winner_roi` | `30` | ROI в %, начиная с которого креатив — победитель |
| `verdict_loser_roi` | `0` | ROI в %, ниже которого креатив — «не зашёл» |
| `burnout_drop_pct` | `30` | Падение CTR в % от пика, при котором срабатывает сигнал выгорания |
| `burnout_min_days` | `5` | Минимум дней с метриками для анализа выгорания |
| `no_results_reminder_days` | `3` | Через сколько дней после приёмки напоминать байеру внести результаты |
| `currency` | `₽` | Валюта метрик расхода/дохода (только для отображения) |

**Миграция существующих данных:**
- В `offers` — все уникальные значения `tasks.offer`.
- В `ai_services` — все значения константы `AI_SERVICES` из `domain.js` и все уникальные `ai_expenses.service`; цена по умолчанию 0 (в демо-сиде — реальные примерные цены).
- После миграции список AI-сервисов на клиенте берётся из таблицы, а не из константы.


Креативщик при сдаче указывает, сколько часов чистого времени ушло на этот раунд. Нужно для честной себестоимости (F11): календарное время «В работе» включает ночи и выходные, поэтому для денег не годится.

### 2.5. Креативы (новая центральная таблица)

```sql
CREATE TABLE IF NOT EXISTS creatives (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id            INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  submission_id      INTEGER NOT NULL REFERENCES submissions(id) ON DELETE CASCADE,
  file_id            INTEGER REFERENCES files(id) ON DELETE SET NULL,  -- либо файл...
  link               TEXT,                                             -- ...либо ссылка (ровно одно из двух)
  title              TEXT NOT NULL,          -- по умолчанию: имя файла / домен ссылки; можно переименовать
  slot               INTEGER NOT NULL,       -- порядковый номер внутри задачи (1..N), связывает версии одного креатива
  version            INTEGER NOT NULL,       -- = submissions.round + 1
  author_id          INTEGER NOT NULL REFERENCES users(id),
  buyer_id           INTEGER NOT NULL REFERENCES users(id),   -- денормализация из задачи для быстрых фильтров
  offer_id           INTEGER REFERENCES offers(id),
  approach_id        INTEGER REFERENCES approaches(id),
  geo                TEXT NOT NULL,
  creative_type      TEXT NOT NULL,
  parent_creative_id INTEGER REFERENCES creatives(id),        -- для вариаций (= tasks.parent_creative_id)
  status             TEXT NOT NULL DEFAULT 'draft'
                     CHECK (status IN ('draft','superseded','accepted','in_test','winner','average','loser','burned','archived')),
  suggested_verdict  TEXT CHECK (suggested_verdict IN ('winner','average','loser')),
  burnout_detected_at TEXT,
  tags               TEXT NOT NULL DEFAULT '',  -- через запятую, нижний регистр
  created_at         TEXT NOT NULL,
  accepted_at        TEXT,
  launched_at        TEXT,
  verdict_at         TEXT,
  updated_at         TEXT NOT NULL,
  CHECK ((file_id IS NOT NULL) OR (link IS NOT NULL))
);
CREATE INDEX IF NOT EXISTS idx_cr_task   ON creatives(task_id);
CREATE INDEX IF NOT EXISTS idx_cr_status ON creatives(status);
CREATE INDEX IF NOT EXISTS idx_cr_buyer  ON creatives(buyer_id);
```

Код креатива не хранится — он вычисляется: `'CD-' + id`.

**Миграция существующих данных:** для всех существующих сдач создать креативы из их файлов-результатов (`files.kind = 'result'`) и ссылок (`submissions.links`, по одной на строку). Для задач в статусе `done` креативы последнего раунда → `accepted` (`accepted_at = tasks.completed_at`), креативы предыдущих раундов → `superseded`. Для остальных задач — `draft`.

### 2.6. Метрики креативов

```sql
CREATE TABLE IF NOT EXISTS creative_metrics (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  creative_id INTEGER NOT NULL REFERENCES creatives(id) ON DELETE CASCADE,
  date        TEXT NOT NULL,                 -- 'YYYY-MM-DD'
  impressions INTEGER NOT NULL DEFAULT 0 CHECK (impressions >= 0),
  clicks      INTEGER NOT NULL DEFAULT 0 CHECK (clicks >= 0),
  conversions INTEGER NOT NULL DEFAULT 0 CHECK (conversions >= 0),
  spend       REAL    NOT NULL DEFAULT 0 CHECK (spend >= 0),
  revenue     REAL    NOT NULL DEFAULT 0 CHECK (revenue >= 0),
  source      TEXT NOT NULL DEFAULT 'manual' CHECK (source IN ('manual','csv')),
  created_by  INTEGER NOT NULL REFERENCES users(id),
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  UNIQUE (creative_id, date)
);
```

Производные показатели **не хранятся**, считаются при чтении (функция `computeMetrics(rows)` в новом файле `server/metrics.js`):

| Показатель | Формула | Если знаменатель 0 |
|---|---|---|
| CTR | clicks / impressions × 100 | `null` (показывать «—») |
| CR | conversions / clicks × 100 | `null` |
| CPA | spend / conversions | `null` |
| ROI | (revenue − spend) / spend × 100 | `null` |
| Profit | revenue − spend | 0 |

Валидация строки: `clicks ≤ impressions`, `conversions ≤ clicks`, дата не в будущем.

### 2.11. Жизненный цикл креатива (диаграмма состояний)

```
                 сдача (submit)
                      │
                      ▼
   ┌──────────── draft ──────────────┐
   │ новая версия того же slot       │ задача принята (accept)
   ▼ (после правок)                  ▼
superseded                       accepted
                                     │ «Запущен» вручную ИЛИ внесены первые метрики
                                     ▼
                                  in_test
                     ┌───────────────┼───────────────┐
                     ▼               ▼               ▼
                  winner          average          loser
                     │ «Выгорел» (вручную, обычно после сигнала F10)
                     ▼
                  burned
   Из accepted / in_test / winner / average / loser / burned → archived («В архив», обратимо: «Вернуть из архива» → предыдущий статус)
```

Правила переходов:
- `draft → superseded`: автоматически, когда для той же задачи и того же `slot` создаётся креатив новой версии.
- `draft → accepted`: автоматически при приёмке задачи — для креативов **последнего** раунда. Все оставшиеся `draft` этой задачи → `superseded`.
- `accepted → in_test`: вручную (кнопка «Запущен в тест») или автоматически при первой записи метрик. Ставит `launched_at`.
- `in_test → winner | average | loser`: только вручную байером/руководителем. Система лишь **предлагает** вердикт (`suggested_verdict`, см. F3). Ставит `verdict_at`.
- Вердикт можно поменять между `winner / average / loser` в любой момент (с записью в историю).
- `winner → burned`: вручную.
- Любой статус кроме `draft` и `superseded` → `archived` и обратно. Для возврата храни предыдущий статус в `history.details` и восстанавливай из последней записи `archived`.
- Удаление задачи каскадно удаляет её креативы (уже так из-за `ON DELETE CASCADE`). Удалять задачу, у креативов которой есть метрики, **запрещено** (ответ 409 с понятным сообщением) — это потеря данных о результатах.

Эта логика — в `server/domain.js`: `CREATIVE_STATUSES`, `allowedCreativeActions(creative, user)`, `canTransitionCreative(from, to)`.

### F1. Справочники и настройки (P0, фаза 1)

**Зачем.** Офферы и подходы сейчас пишутся текстом с опечатками — по ним нельзя строить аналитику. Цены AI-кредитов нужны для себестоимости. Ставки и мощность креативщиков — для планирования.

**Истории.**
- Как руководитель, я веду список офферов и подходов, чтобы все задачи и креативы были размечены одинаково.
- Как руководитель, я задаю цену кредита каждого AI-сервиса, ставку и мощность каждого креативщика.
- Как руководитель, я настраиваю пороги вердикта и выгорания под нашу вертикаль.

**Интерфейс — `/settings`, вкладки:**
1. **Офферы** — таблица (название, вертикаль, активен, кол-во задач). Добавить / переименовать / деактивировать. Удалять нельзя, если есть задачи — только деактивировать. Неактивные не показываются в выпадающих списках, но остаются в старых задачах и фильтрах.
2. **Подходы** — то же (название, описание, активен).
3. **AI-сервисы** — название, цена кредита в ₽ (редактируется прямо в ячейке), активен.
4. **Команда** — пользователи: имя, роль, ставка ₽/ч, мощность (units), WIP-лимит (пусто = по умолчанию). Редактирование в ячейке. Создание пользователей **не требуется**.
5. **Пороги** — форма с ключами из `settings` (раздел 2.1) с подписями-пояснениями человеческим языком, например: «Креатив считается победителем, если ROI ≥ __ %».
6. **Профиль** (все роли) — подключение Telegram (F13), выбор темы (F14).

**API.**
```
GET    /api/dictionaries                 → { offers, approaches, aiServices, creativeTypes, geos, settings }  (все роли; цены AI-сервисов только для lead и buyer)
POST   /api/offers         {name, vertical}                     (lead)
PATCH  /api/offers/:id     {name?, vertical?, is_active?}       (lead)
POST   /api/approaches     {name, description}                  (lead)
PATCH  /api/approaches/:id {...}                                (lead)
POST   /api/ai-services    {name, credit_price_rub}             (lead)
PATCH  /api/ai-services/:id {...}                               (lead)
PATCH  /api/users/:id      {hourly_rate_rub?, capacity_units?, wip_limit?}  (lead)
PATCH  /api/settings       { key: value, ... }                  (lead; только известные ключи, числа валидируются)
```
Существующий `GET /api/meta` оставить, но пусть берёт AI-сервисы из таблицы.

**Изменения в форме ТЗ (`TaskForm.jsx`):** поле «Оффер» становится выпадающим списком с поиском из справочника; добавляются поля «Подход» (выпадающий список, необязательный), «Язык», «Формат», «Хук / ключевая идея», «Трудоёмкость» (F8).

**Критерии приёмки.**
- [ ] Старая БД после запуска новой версии содержит все прежние офферы в справочнике, у всех задач проставлен `offer_id`.
- [ ] Деактивированный оффер пропадает из формы новой задачи, но старые задачи с ним открываются и фильтруются.
- [ ] Байер получает 403 на `POST /api/offers`.
- [ ] Изменение цены AI-сервиса сразу меняет себестоимость в аналитике (F11).
- [ ] `PATCH /api/settings` с неизвестным ключом или нечисловым значением → 400.

### F2. Креативы и Библиотека (P0, фаза 2)

**Зачем.** Сейчас результаты работы — это файлы, «похороненные» внутри задач. Нельзя ответить на вопрос «покажи все видео под Бразилию по офферу X» или «что мы уже делали с подходом „Отзыв“». Библиотека — это память отдела.

**Истории.**
- Как байер, я нахожу все креативы по офферу и GEO, чтобы не заказывать то, что уже было.
- Как креативщик, я смотрю лучшие креативы команды по нужному подходу для вдохновения.
- Как руководитель, я вижу каждый креатив вместе с его историей: задача, версии, результаты, вариации.

**Как создаются креативы (изменение существующего `POST /api/tasks/:id/submit`):**
- В форму сдачи (сейчас: файлы, ссылки, комментарий, AI-расходы) добавляется поле **«Часов потрачено»** (число ≥ 0, шаг 0,5, обязательное).
- При сдаче раунда 0 каждый файл-результат и каждая ссылка (по строке) превращаются в отдельный креатив со `slot` = 1..N в порядке загрузки.
- При сдаче после правок (раунд ≥ 1) в форме сдачи для каждого нового файла/ссылки креативщик выбирает: **«Новая версия креатива №…»** (выпадающий список слотов прошлого раунда с превью) или **«Новый креатив»**. По умолчанию — сопоставление по порядку. Новая версия получает тот же `slot`, `version = round + 1`; прежняя версия этого слота → `superseded`. Слоты прошлого раунда, для которых новой версии не прислали, остаются `draft` и при приёмке тоже станут `accepted` (замечаний к ним не было).

  > Уточнение к правилу 2.11: при приёмке `accepted` становится **последняя версия каждого слота**, а не только креативы последнего раунда.

- Креатив наследует из задачи: `buyer_id`, `offer_id`, `approach_id`, `geo`, `creative_type`, `parent_creative_id`; `author_id` = сдавший креативщик.

**Интерфейс — `/library`:**
- Сетка карточек (на мобильном — 1 колонка, на десктопе — 3–5 по ширине).
- **Карточка:** превью (картинка → `<img>` с `object-fit: cover`; видео → `<video muted preload="metadata">`, проигрывается при наведении; ссылка → иконка и домен), код `CD-142`, название, бейдж статуса (цвета: draft — серый, accepted — синий, in_test — фиолетовый, winner — зелёный, average — жёлтый, loser — красный, burned — оранжевый, archived — приглушённый), чипы оффер · GEO · тип, автор (аватар-инициалы). Если есть метрики — ROI и CTR крупно. Если сработал сигнал выгорания — оранжевая иконка пламени.
- **Фильтры** (над сеткой, сохраняются в URL query, чтобы ссылкой можно было поделиться): поиск (код, название, теги), оффер, GEO, тип, подход, автор, байер, статус (мультивыбор), период создания. По умолчанию скрыты `draft`, `superseded`, `archived` (переключатель «Показать черновики и архив»).
- **Сортировка:** новые / ROI ↓ / расход ↓ / CTR ↓.
- Над сеткой — сводка по текущему фильтру: «Найдено 48 · в тесте 12 · победителей 7 (14,6 %) · средний ROI 23,4 %».

**Интерфейс — страница креатива `/library/:id`:**
- Слева: большое превью (картинка/видео-плеер/ссылка-кнопка) со слоем пинов (F7). Под ним — переключатель версий «v1 · v2 · v3» (все версии этого `slot` в этой задаче), выбранная версия показывается в превью.
- Справа:
  - Заголовок: код (кнопка «скопировать код» — копирует `CD-142` в буфер, тост «Код скопирован — вставьте его в название объявления»), название (редактируется по клику — для байера/lead), статус, кнопки действий по `allowedCreativeActions`: «Запущен в тест», вердикты, «Выгорел», «Сделать вариации» (F4), «В архив», «Скачать».
  - Свойства: оффер, GEO, тип, подход, автор, байер, задача (ссылка на карточку задачи на доске), даты (создан, принят, запущен, вердикт), теги (редактирование чипами).
  - Блок «Результаты» (F3).
  - Блок «Себестоимость» (F11).
  - Блок «Семейство»: родитель (если вариация) и дочерние вариации — мини-карточки с вердиктами и ROI. Это дерево показывает, как развивалась идея.
  - История по креативу (записи `history` с этим `creative_id`).
- В модалке задачи на доске (`TaskModal.jsx`) в блоке сдач у каждого файла/ссылки появляется код креатива и ссылка «Открыть в библиотеке».

**API.**
```
GET   /api/creatives?offer_id=&geo=&type=&approach_id=&author_id=&buyer_id=&status=a,b&q=&from=&to=&sort=new|roi|spend|ctr&limit=60&offset=0
      → { items: [ {creative + preview_url + metrics_summary{impressions,clicks,conversions,spend,revenue,ctr,cr,cpa,roi} + burnout:boolean} ], total, summary }
GET   /api/creatives/:id   → { creative, versions[], metrics[], metrics_summary, family{parent, children[]}, annotations[], cost, history[], actions[] }
PATCH /api/creatives/:id   { title?, tags?, approach_id? }          (байер-владелец / lead)
POST  /api/creatives/:id/status { to: 'in_test'|'winner'|'average'|'loser'|'burned'|'archived'|'restore' }
```
Файлы отдаются существующим `GET /api/files/:id`.

**Критерии приёмки.**
- [ ] Сдача 3 файлов и 2 ссылок в раунде 0 создаёт 5 креативов со слотами 1–5 в статусе `draft`.
- [ ] Сдача после правок с сопоставлением «новая версия слота 2» делает прежнюю версию слота 2 `superseded`, новая — `version = 2`.
- [ ] После приёмки все последние версии слотов — `accepted`, остальные — `superseded`.
- [ ] Креативщик получает 403 на смену статуса креатива; байер — 403 на чужой креатив.
- [ ] Фильтры библиотеки отражаются в URL; открытие такой ссылки восстанавливает фильтр.
- [ ] Удаление задачи, у креативов которой есть метрики, → 409.
- [ ] Миграция: креативы созданы для всех существующих сдач демо-базы.

### F3. Результаты тестов и вердикты (P0, фаза 3)

**Зачем.** Главный недостающий кусок: сервис не знает, сработал ли креатив. Без этого нельзя оценить ни креативщика, ни подход, ни качество ТЗ по бизнес-результату.

**Истории.**
- Как байер, я вношу статистику креатива за день прямо в его карточке.
- Как байер, я загружаю CSV-выгрузку из трекера, и статистика сама раскладывается по креативам по их кодам.
- Как байер, я вижу предложенный системой вердикт и подтверждаю его одним кликом.

**Интерфейс — блок «Результаты» на странице креатива:**
- Сводка крупными цифрами: Расход · Доход · Профит · ROI · CTR · CR · CPA (за всё время).
- Мини-график CTR и ROI по дням (inline SVG, две линии, ось дат; при наведении — значения за день).
- Таблица по дням (дата, показы, клики, конв., расход, доход, CTR, ROI) с редактированием строки и удалением (байер-владелец/lead).
- Форма «Добавить день»: дата (по умолчанию вчера), 5 числовых полей. Если на эту дату строка уже есть — форма предупреждает и обновляет её.
- Если `suggested_verdict` задан, а вердикта ещё нет: плашка «Система предлагает: **Победитель** (ROI 47,2 % при расходе 180 ₽). [Подтвердить] [Выбрать другой]».

**Интерфейс — импорт CSV:** кнопка «Импорт результатов» в Библиотеке (байер, lead) → модалка:
1. Выбор файла. Подсказка с примером формата и кнопкой «Скачать шаблон CSV».
2. **Предпросмотр** (сервер вызывается с `dry_run=1`): таблица «будет добавлено N строк, обновлено M, ошибок K», ошибки с номером строки и причиной («строка 7: креатив CD-999 не найден», «строка 12: клики больше показов», «строка 15: креатив CD-88 принадлежит другому байеру»).
3. Кнопка «Импортировать» (активна, если есть хотя бы одна валидная строка; ошибочные строки пропускаются).

Формат CSV: разделитель `,` или `;` (определять автоматически по первой строке), кодировка UTF-8 (с BOM или без), первая строка — заголовки. Обязательные колонки (регистр не важен, допускаются русские синонимы):

| Колонка | Синонимы | Значение |
|---|---|---|
| `creative` | `креатив`, `code`, `код` | `CD-142` или `142`. Также искать код внутри строки (`BR_nutra_CD-142_v2` → 142) регулярным выражением `CD-(\d+)` — так байер может выгрузить отчёт по названиям объявлений как есть |
| `date` | `дата` | `YYYY-MM-DD` или `DD.MM.YYYY` |
| `impressions` | `показы` | целое |
| `clicks` | `клики` | целое |
| `conversions` | `конверсии`, `leads` | целое |
| `spend` | `расход`, `cost` | число, допускается запятая как десятичный разделитель |
| `revenue` | `доход` | число |

Если в файле несколько строк на один креатив и дату — суммировать их.

**API.**
```
GET    /api/creatives/:id/metrics
PUT    /api/creatives/:id/metrics/:date   {impressions, clicks, conversions, spend, revenue}   (upsert)
DELETE /api/creatives/:id/metrics/:date
POST   /api/metrics/import?dry_run=1|0    multipart: file
       → { added, updated, skipped, errors: [{row, message}], affected_creatives: [ids] }
GET    /api/metrics/template.csv
```

**Бизнес-правила.**
- Первые метрики у креатива в статусе `accepted` переводят его в `in_test` (с записью в историю «запущен в тест автоматически»).
- Метрики можно вносить для креативов в статусах `accepted`, `in_test`, `winner`, `average`, `loser`, `burned`. Для `draft`/`superseded`/`archived` — 409.
- **Предложение вердикта** пересчитывается после каждого изменения метрик (функция `suggestVerdict(summary, settings)` в `server/metrics.js`):
  - если суммарный расход < `verdict_min_spend` → `suggested_verdict = NULL` (данных мало);
  - иначе ROI ≥ `verdict_winner_roi` → `winner`; ROI < `verdict_loser_roi` → `loser`; иначе `average`.
- Система **никогда не ставит вердикт сама**, только предлагает. Если поставленный вердикт расходится с предложением — на карточке маленькая подсказка «по данным — средний».
- Импорт выполняется в одной транзакции; в историю пишется одна запись `metrics_imported` с числом строк и списком креативов, а не запись на каждую строку.

**Критерии приёмки.**
- [ ] Ввод строки с кликами больше показов → 400.
- [ ] Первые метрики переводят `accepted` → `in_test`.
- [ ] При расходе 40 (порог 50) вердикт не предлагается; после добавления дня с расходом 20 и ROI 35 % предлагается `winner`.
- [ ] CSV с `;`, датами `DD.MM.YYYY`, запятыми в числах и кодом внутри названия объявления импортируется корректно.
- [ ] `dry_run=1` ничего не записывает в БД.
- [ ] Байер не может импортировать метрики для чужого креатива (строка уходит в ошибки, остальные импортируются).
- [ ] Повторный импорт того же файла даёт `updated`, а не дубли.

### F4. «Сделать вариации» победителя (P0, фаза 3)

**Зачем.** Креативы-победители быстро выгорают, и главная работа баинга — быстро получить новые вариации того, что работает. Сейчас байер пишет такое ТЗ с нуля и теряет связь с исходником.

**Истории.**
- Как байер, я нажимаю «Сделать вариации» у победителя, и через 10 секунд ТЗ на вариации отправлено креативщикам.
- Как креативщик, в задаче-вариации я сразу вижу исходный креатив и его результаты.
- Как руководитель, я вижу «семейные деревья» креативов и какие вариации превзошли оригинал.

**Интерфейс.**
- Кнопка «Сделать вариации» на странице креатива и в меню карточки в Библиотеке. Доступна для `winner`, `average` и `burned` (у `burned` она выделена — это основной сценарий).
- Открывается обычная форма ТЗ, **предзаполненная**: оффер, GEO, тип, подход, язык, формат — из креатива; заголовок «Вариации CD-142: <название>»; количество 3; приоритет «высокий»; дедлайн +48 ч; описание — шаблон:
  ```
  Сделать вариации креатива-победителя CD-142.
  Результат оригинала: ROI 47 %, CTR 2,3 % (расход 18 400 ₽).
  Сохранить: <подход> и <хук из исходного ТЗ>.
  Изменить: ______ (визуал / первые 3 секунды / оффер-подачу / персонажа)
  ```
  Исходный креатив автоматически прикреплён как референс (показывается превью, а не просто ссылка).
- Байер правит и отправляет. Задача создаётся с `parent_creative_id` и `iteration = (iteration задачи исходного креатива) + 1`.
- На карточке задачи на доске — бейдж «Итерация 2 · от CD-142». В модалке задачи — блок «Исходный креатив» с превью, ROI, CTR и ссылкой.
- Креативы, сданные по такой задаче, получают `parent_creative_id`, и в блоке «Семейство» появляется дерево.
- В блоке «Семейство» у каждой вариации подсветка: ROI выше родителя — зелёная стрелка вверх, ниже — красная вниз.

**API.**
```
GET /api/creatives/:id/variation-draft   → объект-черновик для формы ТЗ (сервер собирает текст и поля)
POST /api/tasks  (существующий) принимает parent_creative_id; сервер сам вычисляет iteration и прикрепляет референс.
```

**Критерии приёмки.**
- [ ] Задача из «Сделать вариации» имеет `parent_creative_id` и правильный `iteration`.
- [ ] Креативы, сданные по задаче-вариации, наследуют `parent_creative_id`.
- [ ] На странице родителя в «Семействе» видны дочерние креативы с ROI и стрелками сравнения.
- [ ] Кнопка недоступна у `draft`, `accepted`, `in_test`, `loser` (у `loser` вариации бессмысленны).

### F5. «Моя очередь» — стартовая страница по ролям (P0, фаза 4)

**Зачем.** Канбан показывает всё сразу, но человек приходит утром с вопросом «что мне делать прямо сейчас?». У каждой роли свой ответ.

**Общее.** Страница `/queue`, состоит из блоков-списков. Каждый блок: заголовок, счётчик, до 5 элементов + «Показать все» (ведёт на доску/библиотеку с нужным фильтром). Пустой блок показывает дружелюбную пустую подсказку («Всё проверено 🎉» — единственное место, где допустим эмодзи). Порядок блоков — по срочности. Обновление каждые 20 секунд, как у доски.

**Креативщик видит:**
1. **Правки — ждут вас** (задачи `revision`, где он исполнитель): сколько пинов открыто, комментарий байера одной строкой, кнопка «Начать правки».
2. **В работе** (его `in_progress` и `revision` с начатой доработкой): по возрастанию дедлайна, полоса «осталось времени» (зелёная > 50 %, жёлтая 20–50 %, красная < 20 % или просрочено), кнопка «Сдать».
3. **Можно взять** (`new`): по приоритету, затем дедлайну; трудоёмкость в units; если он на WIP-лимите — кнопка «Взять» неактивна с подсказкой «Сначала сдайте одну из текущих задач (лимит 3)».
4. **Мои показатели за 30 дней:** сдано задач, % в срок, % с правками, креативов в тесте, победителей (и % от протестированных). Сравнение с прошлыми 30 днями стрелкой.

**Байер видит:**
1. **Ждут вашей проверки** (`review`, его задачи): сколько ждут (красным, если > 24 ч), кнопки «Открыть», «Принять».
2. **Выгорают** (его креативы с сигналом выгорания, F10): падение CTR в %, кнопка «Сделать вариации».
3. **Внесите результаты** (его креативы `accepted` старше `no_results_reminder_days` дней без метрик, и `in_test` без новых метрик 3+ дня): кнопка «Внести».
4. **Ждут вердикта** (есть `suggested_verdict`, нет вердикта): предложение и кнопка «Подтвердить».
5. **Мои задачи в работе** (`new`, `in_progress`, `revision`): статус, исполнитель, дедлайн.
6. **Победители за 7 дней** (его креативы, получившие `winner`): мини-карточки.

**Руководитель видит («Пожары»):**
1. **Просрочено** — задачи с истёкшим дедлайном не в `done`.
2. **Горит без исполнителя** — `new`, до дедлайна < 24 ч.
3. **Зависло на проверке** — `review` > 24 ч (с именем байера, который не проверяет).
4. **Перегруз** — креативщики с загрузкой > 100 % мощности (F8), **простаивают** — с нулевой загрузкой.
5. **Выгорающие победители** — по всей команде.
6. **KPI недели** (плитки): задач создано / сдано, % в срок, % с правками, победителей, расходы на AI в ₽, средняя себестоимость креатива. Сравнение с прошлой неделей.

**API.**
```
GET /api/queue   → { role, blocks: [ { key, title, count, items: [...] } ] }
```
Сервер собирает блоки по роли; клиент только отрисовывает. Ключи блоков фиксированы (`revisions_waiting`, `in_work`, `available`, `my_stats`, `to_review`, `burning`, `need_results`, `need_verdict`, `my_tasks`, `recent_winners`, `overdue`, `urgent_unassigned`, `stuck_review`, `load_issues`, `team_burning`, `week_kpi`).

**Критерии приёмки.**
- [ ] После входа любой ролью открывается `/queue`.
- [ ] Креативщик на WIP-лимите видит неактивную кнопку «Взять» с подсказкой; сервер также отклоняет `take` (409).
- [ ] Задача на проверке > 24 ч попадает к руководителю в «Зависло на проверке».
- [ ] Принятый 4 дня назад креатив без метрик появляется у байера в «Внесите результаты».

### F6. Шаблоны ТЗ и проверка качества ТЗ (P0, фаза 4)

**Зачем.** Плохое ТЗ — главная причина правок. Шаблоны ускоряют постановку, проверка по чек-листу подсказывает, чего не хватает, до отправки.

**Истории.**
- Как байер, я создаю ТЗ из шаблона или копирую своё прошлое ТЗ за 30 секунд.
- Как байер, при заполнении ТЗ я вижу, чего не хватает, чтобы креативщику не пришлось переспрашивать.
- Как руководитель, я вижу, что ТЗ с низкой оценкой дают больше правок (и могу показать это байерам).

**Шаблоны — интерфейс.**
- В форме нового ТЗ сверху: выпадающий список «Из шаблона…» (сначала личные, затем общие, сортировка по `use_count`) и кнопка «Скопировать прошлое ТЗ» (поиск по своим последним 20 задачам).
- Внизу формы: «Сохранить как шаблон» (имя шаблона; у lead — галочка «Общий для всех»).
- Управление шаблонами — вкладка в `/settings` «Шаблоны ТЗ» (байер — свои, lead — все): список, переименовать, удалить, сделать общим (lead).
- В модалке существующей задачи — действие «Дублировать» (байер-владелец, lead): открывает форму, заполненную полями задачи (без файлов-референсов, но со ссылками).
- Применение шаблона заполняет только **пустые** поля формы; если поля уже заполнены — спросить «Заменить заполненные поля?».

**Проверка качества — правила** (функция `scoreBrief(task)` в `server/domain.js`, **та же функция используется на клиенте** — вынести в общий модуль, который импортируют и сервер, и клиент, например `shared/brief.js`; в Vite настроить алиас):

| # | Проверка | Вес | Подсказка, если не выполнено |
|---|---|---|---|
| 1 | Оффер выбран из справочника | 10 | «Выберите оффер из списка» |
| 2 | Описание ≥ 80 символов | 20 | «Опишите задачу подробнее: что показать, кому, какое действие» |
| 3 | Указан хук / ключевая идея | 15 | «Какая мысль должна зацепить в первые 3 секунды?» |
| 4 | Выбран подход | 10 | «Выберите подход — так проще анализировать результаты» |
| 5 | Есть хотя бы один референс (ссылка или файл) | 15 | «Добавьте пример — референс экономит круг правок» |
| 6 | Указан язык | 10 | «На каком языке текст и озвучка?» |
| 7 | Указан формат (для Видео/UGC/Анимации — ещё и длительность: регулярка `\d+\s*(с|сек|s|sec)` в поле формата или описании) | 10 | «Укажите размеры и длительность» |
| 8 | Дедлайн не раньше чем через 4 часа от создания (или приоритет «срочно») | 10 | «Слишком короткий срок — поставьте приоритет „Срочно“ или сдвиньте дедлайн» |

Сумма весов = 100. Результат — `brief_score` 0–100.

**Интерфейс проверки.** Справа от формы (на мобильном — над кнопкой «Создать») панель «Качество ТЗ»: круговой индикатор (красный < 60, жёлтый 60–79, зелёный ≥ 80) и чек-лист с галочками, обновляется при вводе. **Отправку не блокирует.** При `brief_score < 60` кнопка «Создать» показывает подтверждение «ТЗ заполнено на 45 %. Креативщику может не хватить информации. Отправить всё равно?». На карточке задачи на доске оценка не показывается (чтобы не стыдить), в модалке задачи — показывается.

**API.**
```
GET    /api/templates               (свои + общие; lead — все)
POST   /api/templates               {name, is_shared?, ...поля}
PATCH  /api/templates/:id
DELETE /api/templates/:id
POST   /api/templates/:id/use       → инкремент use_count, возвращает поля для формы (с вычисленным дедлайном)
GET    /api/tasks/:id/duplicate     → поля для формы
```
`POST /api/tasks` и `PATCH /api/tasks/:id` пересчитывают и сохраняют `brief_score` на сервере (клиентскому значению не доверять).

**Критерии приёмки.**
- [ ] Шаблон с `deadline_hours = 48` при применении даёт дедлайн «сейчас + 48 ч».
- [ ] Байер не видит чужие личные шаблоны и получает 403 на их изменение.
- [ ] Серверный и клиентский `scoreBrief` дают одинаковый результат (одна функция).
- [ ] ТЗ без описания, хука и референсов получает ≤ 40 баллов и показывает подтверждение при отправке.

### F7. Ревью с пинами на креативе (P1, фаза 5)

**Зачем.** Правки вида «переделай, не то» дают ещё круг правок. Замечание, поставленное прямо на точку картинки или секунду видео, однозначно.

**Истории.**
- Как байер, я кликаю по месту на картинке или ставлю видео на паузу и пишу замечание именно к этому месту.
- Как креативщик, я вижу все замечания на самом креативе и отмечаю исправленные.

**Интерфейс.**
- В модалке задачи в статусе `review` у каждого креатива последней сдачи — кнопка «Ревью» → полноэкранный режим просмотра (также доступен со страницы креатива):
  - **Картинка:** клик по изображению → в этой точке появляется нумерованный кружок и поле ввода замечания. Координаты сохраняются в долях (0..1), чтобы пин стоял на месте при любом размере экрана.
  - **Видео:** свой плеер поверх `<video>`: play/pause, полоса прогресса. На паузе клик по кадру ставит пин с `time_sec` = текущее время. На полосе прогресса — засечки в местах пинов; клик по засечке перематывает и показывает пин.
  - **Ссылка:** только общие замечания (без координат).
  - Кнопка «Общее замечание» — пин без координат.
  - Справа список замечаний: номер, текст, автор, время (для видео — «0:07»), статус. Клик по замечанию подсвечивает пин.
- Кнопка «На правки» в модалке задачи: комментарий к правкам **становится необязательным, если есть хотя бы один открытый пин** в текущем раунде (сейчас он обязателен всегда — изменить правило). Открытые пины автоматически перечисляются в записи о правках: «Замечания: 3 на CD-142, 1 на CD-143».
- На новой версии креатива показываются пины предыдущей версии полупрозрачными с пометкой «к прошлой версии» — креативщик сверяется, всё ли исправил.
- Креативщик (исполнитель) может отметить пин «Исправлено» (`resolved`); байер может вернуть его в `open`.
- Счётчик открытых пинов — на карточке задачи на доске (иконка-пин с числом) и в блоке «Правки — ждут вас» в «Моей очереди».

**API.**
```
GET    /api/creatives/:id/annotations?round=
POST   /api/creatives/:id/annotations   {x?, y?, time_sec?, text}
PATCH  /api/annotations/:id             {text?, status?}
DELETE /api/annotations/:id             (только автор и только пока задача в review)
```

**Бизнес-правила.**
- Ставить пины можно, только пока задача в `review` (иначе 409), и только байеру-владельцу и lead.
- `round` пина = раунд сдачи, к которой относится версия креатива.
- Изменение правила обязательности комментария при `revision` — в существующем обработчике `POST /api/tasks/:id/revision`.

**Критерии приёмки.**
- [ ] Пин на картинке, поставленный на широком экране, отображается в той же точке изображения на мобильном.
- [ ] Пин на видео с `time_sec = 7.2` перематывает плеер на 0:07.
- [ ] «На правки» без комментария, но с открытым пином → успешно; без комментария и без пинов → 400.
- [ ] Креативщик не может создать пин (403), но может отметить пин исправленным, если он исполнитель.

### F8. Трудоёмкость, WIP-лимит и «Загрузка команды» (P1, фаза 5)

**Зачем.** «5 баннеров» и «1 плейабл» — несравнимые по объёму задачи, а сейчас обе считаются как «1 задача». Руководителю нужно видеть реальную загрузку и знать, кому отдать срочную задачу.

**Трудоёмкость.**
- Веса типов (константа `TYPE_UNITS` в `domain.js`): Статика 1, Баннер 1, Иконки/скриншоты 1, Анимация 2, UGC 3, Видео 3, Прелендинг 4, Плейабл 5.
- При создании задачи `estimate_units` по умолчанию = вес типа × количество (форма пересчитывает при смене типа/количества, пока пользователь не изменил поле вручную). Байер и lead могут поправить.
- **Загрузка креативщика** = сумма `estimate_units` его задач в `in_progress` и `revision`. **Процент загрузки** = загрузка / `capacity_units` × 100.

**WIP-лимит.**
- Число задач креативщика в `in_progress` + (`revision` с начатой доработкой) не может превышать его `wip_limit` (или `wip_limit_default`).
- Действие `take` (взять новую задачу или начать правки) при достигнутом лимите → 409: «Достигнут лимит одновременных задач (3). Сдайте одну из текущих задач». **Исключение:** начать правки по своей задаче можно всегда (правки приоритетнее новых задач) — лимит проверяется только при взятии `new`.
- Руководитель при назначении (`assign`) может превысить лимит: модалка предупреждает «У Анны уже 3 задачи (лимит 3). Назначить всё равно?».

**Подсказка исполнителя** (в модалке назначения у руководителя, функция `suggestAssignees(task)`):
- Для каждого креативщика: `score = 0.5 × свободная_доля + 0.3 × опыт_в_типе + 0.2 × доля_победителей_в_типе`, где
  - свободная доля = max(0, 1 − загрузка / мощность);
  - опыт в типе = доля принятых задач этого `creative_type` среди всех его принятых задач за 60 дней;
  - доля победителей в типе = winners / (winners + average + loser) по его креативам этого типа за 90 дней (0, если тестов нет).
- Список сортируется по score, у первого — бейдж «Рекомендуем». Под каждым именем — **объяснение человеческим языком**: «Свободно 6 из 10 units · 12 видео за 2 месяца · 33 % победителей». Объяснение важнее числа — показывать сам score не нужно.

**Интерфейс — `/team`:**
- Карточка на каждого креативщика: аватар, имя, должность; полоса загрузки (units / мощность, цвет: < 70 % зелёный, 70–100 % жёлтый, > 100 % красный); «в работе N задач из лимита M»; «освободится ориентировочно: <дата>» (самый поздний дедлайн среди активных задач; если дедлайнов нет — «—»).
- Под карточками — **таймлайн на 14 дней** (упрощённая диаграмма Ганта): строки — креативщики, полосы — активные задачи от `taken_at` до `deadline`, цвет по приоритету, просроченная часть — штриховкой. Клик по полосе открывает задачу. Сверху — вертикальная линия «сейчас».
- Отдельная строка «Без исполнителя»: задачи `new` с дедлайнами — чтобы видеть, что скоро «упадёт» на команду.

**API.**
```
GET /api/team               → [{ user, load_units, capacity_units, load_pct, wip_count, wip_limit, free_at, active_tasks[] }], unassigned[]
GET /api/tasks/:id/suggest-assignees → [{ user, score, reasons: [строки], over_limit: bool }]
```

**Критерии приёмки.**
- [ ] Задача «Видео × 2» по умолчанию получает 6 units.
- [ ] Креативщик с 3 задачами в работе (лимит 3) получает 409 при взятии новой, но может начать правки по своей задаче.
- [ ] Руководитель может назначить сверх лимита после подтверждения.
- [ ] Подсказка ставит первым свободного креативщика с опытом в этом типе (проверить на демо-данных).

### F9. Подходы и гипотезы (P1, фаза 5)

**Зачем.** Знание «что работает» сейчас в головах байеров и уходит вместе с ними. Страница подходов делает его общим активом отдела.

**Интерфейс — `/approaches`:**
- Таблица подходов: название, описание, креативов всего, протестировано, победителей, % победителей, средний ROI, суммарный профит, последний победитель (мини-превью). Сортировка по любому столбцу. По умолчанию — по % победителей.

### F10. Сигнал выгорания (P1, фаза 6)

**Зачем.** Байер замечает выгорание креатива по падению показателей с опозданием и теряет деньги. Сервис может заметить это сам и сразу предложить действие — вариации.

**Алгоритм** (функция `detectBurnout(metricsRows, settings)` в `server/metrics.js`), применяется к креативам в статусе `winner`:
1. Если дней с показами > 0 меньше `burnout_min_days` → не анализировать.
2. Считать CTR скользящим окном 3 дня (сумма кликов / сумма показов за 3 дня подряд, только дни с данными).
3. Пик = максимум скользящего CTR. Текущее значение = скользящий CTR последних 3 дней с данными.
4. Если текущее ≤ пик × (1 − `burnout_drop_pct` / 100) → выгорание.

**Поведение.**
- Проверка запускается после каждого изменения метрик креатива и при импорте CSV.
- При первом срабатывании ставится `burnout_detected_at` и создаётся уведомление байеру (F12). Повторно не уведомлять, пока сигнал не снимется.
- Если CTR восстановился (условие перестало выполняться) — `burnout_detected_at` сбрасывается в `NULL`.
- Отображение: иконка пламени на карточке, плашка на странице креатива «CTR упал на 41 % от пика (с 2,9 % до 1,7 %). [Сделать вариации] [Отметить выгоревшим] [Скрыть до новых данных]». «Скрыть» — до следующего изменения метрик.
- Для аналитики фиксировать **время реакции** = от `burnout_detected_at` до создания первой задачи-вариации от этого креатива.

**Критерии приёмки.**
- [ ] Ряд CTR по дням 3,0 / 3,1 / 2,9 / 2,4 / 2,0 / 1,7 (при равных показах) при пороге 30 % даёт сигнал; ряд 3,0 / 2,9 / 2,8 / 2,7 / 2,8 — не даёт.
- [ ] При 4 днях данных (минимум 5) анализа нет.
- [ ] Уведомление о выгорании создаётся один раз.

### F11. Себестоимость креатива и новая аналитика (P1, фаза 6)

**Зачем.** Руководителю нужно говорить с бизнесом деньгами: сколько стоит креатив, сколько стоит победитель, окупается ли отдел.

**Расчёт себестоимости** (функция `computeTaskCost(taskId)` в `server/analytics.js`):
- **Труд** = Σ `submissions.hours_spent` × `hourly_rate_rub` исполнителя (ставка на момент расчёта; хранить историю ставок не нужно).
- **AI** = Σ `ai_expenses.credits` × `ai_services.credit_price_rub` (сопоставление по названию сервиса).
- **Себестоимость задачи** = труд + AI, с разбивкой на основную работу (раунд 0) и правки (раунды ≥ 1).
- **Себестоимость креатива** = себестоимость задачи / число принятых креативов задачи (если принятых нет — / quantity).
- **Стоимость победителя** (для периода) = суммарная себестоимость всех протестированных креативов / число победителей.
- **Стоимость правок** — отдельной строкой: сколько денег «съели» правки.

**Интерфейс.**
- Блок «Себестоимость» на странице креатива и в модалке задачи (видят байер-владелец и lead): «Труд 4,5 ч × 800 ₽ = 3 600 ₽ · AI 1 240 ₽ · Итого 4 840 ₽ · На креатив 1 613 ₽ · из них правки 1 100 ₽». Если ставка креативщика не задана — подсказка «Задайте ставку в настройках».
- Если у креатива есть метрики — рядом «Окупаемость креатива: профит 18 400 ₽ = 11× его стоимости».
- **Новые блоки на `/analytics`** (существующие блоки сохранить):
  1. **Эффективность креативов**: протестировано, победителей, % победителей, средний ROI, суммарный профит по креативам — с динамикой по неделям.
  2. **Рейтинг креативщиков по результату**: креативов сдано, протестировано, % победителей, средний ROI их креативов, средняя себестоимость креатива, % задач с правками. (Сейчас есть только загрузка и скорость — добавляем качество.)
  3. **Деньги отдела**: труд, AI, итого за период; стоимость креатива; стоимость победителя; доля затрат на правки; для сравнения — суммарный профит победителей.
  4. **Качество ТЗ → правки**: 3 столбца по группам `brief_score` (< 60, 60–79, ≥ 80) — % задач с правками и среднее число раундов в каждой группе. Подпись-вывод генерируется автоматически: «ТЗ с оценкой ниже 60 уходят на правки в 2,3 раза чаще».
  5. **Реакция на выгорание**: среднее время от сигнала до заказа вариаций, число выгоревших без реакции.
  6. **Итерации**: средний ROI оригиналов vs вариаций 2-й и 3-й итерации.

**API.**
```
GET /api/analytics?from=&to=   (существующий) — добавить в ответ разделы: creative_performance, creatives_rating, money, brief_quality, burnout_reaction, iterations
GET /api/tasks/:id/cost
```

**Критерии приёмки.**
- [ ] Задача: 3 ч + 1,5 ч по ставке 800 ₽ и 100 кредитов Midjourney по 4 ₽ → себестоимость 4 000 ₽ (3 600 + 400), из них правки 1 200 ₽ (если 1,5 ч — в раунде 1).
- [ ] Креативщик не получает денежные поля (в ответах API для него они отсутствуют, а не просто скрыты на клиенте).
- [ ] Вывод в блоке «Качество ТЗ → правки» не показывается, если в какой-то группе меньше 5 задач.

### F12. Уведомления в приложении (P1, фаза 6)

**Зачем.** Сейчас о событии можно узнать, только открыв доску. Уведомления сокращают ожидание на каждом шаге цикла.

**События и получатели.**

| type | Когда | Кому | Текст (пример) |
|---|---|---|---|
| `task_created` | создана задача без исполнителя | всем креативщикам, у кого загрузка < 100 % | «Новое ТЗ: Видео ×2, BR · срочно» |
| `task_assigned` | назначение | исполнителю | «Вам назначена задача #51» |
| `task_taken` | креативщик взял задачу | байеру | «Анна взяла #51» |
| `task_submitted` | сдача | байеру | «#51 сдана на проверку (раунд 2)» |
| `task_accepted` | приёмка | исполнителю | «#51 принята» |
| `task_revision` | правки | исполнителю | «#51 вернули на правки: 3 замечания» |
| `comment_added` | комментарий | другим участникам задачи (байер, исполнитель, кроме автора) | «Иван: „добавь логотип крупнее“» |
| `deadline_soon` | до дедлайна < 2 ч, задача не на проверке и не готова | исполнителю (или байеру, если исполнителя нет) | «До дедлайна #51 меньше 2 часов» |
| `overdue` | дедлайн прошёл | исполнителю, байеру, lead | «#51 просрочена» |
| `burnout` | сигнал выгорания | байеру | «CD-142 выгорает: CTR −41 %» |
| `need_results` | креатив принят N дней назад без метрик | байеру (раз в день, сводно) | «3 креатива ждут результатов» |

- `deadline_soon` и `overdue` — одноразовые: `dedup_key = '<type>:<task_id>:<user_id>'`. Вставка через `INSERT OR IGNORE`.
- Фоновая проверка дедлайнов и `need_results` — `setInterval` на сервере раз в 5 минут (без внешнего cron), плюс один прогон при старте.
- Уведомление самому себе (автору действия) не создаётся.

**Интерфейс.** Колокольчик в шапке со счётчиком непрочитанных → выпадающая панель: последние 30 уведомлений, непрочитанные выделены, клик открывает задачу/креатив и помечает прочитанным, кнопка «Прочитать все». Опрос `GET /api/notifications?unread_count=1` каждые 20 секунд. Новое уведомление во время работы — всплывающий тост на 5 секунд.

**API.**
```
GET   /api/notifications?limit=30        → { items, unread }
POST  /api/notifications/read            { ids: [...] } | { all: true }
```
Создание — внутренней функцией `notify({ userIds, type, taskId, creativeId, text, dedupKey })` в новом `server/notify.js`, которая также отправляет копию в Telegram (F13), если он подключён.

**Критерии приёмки.**
- [ ] Сдача задачи создаёт уведомление байеру, но не креативщику-автору.
- [ ] Уведомление `overdue` создаётся ровно один раз на пользователя и задачу, даже после нескольких прогонов проверки.
- [ ] Счётчик в шапке уменьшается после открытия уведомления.

### F13. Telegram-бот (P2, фаза 7)

**Зачем.** В медиабаинге рабочая коммуникация живёт в Telegram. Если байер может принять работу кнопкой прямо в мессенджере, цикл сокращается на часы.

**Включение.** Функция работает, только если задана переменная окружения `TELEGRAM_BOT_TOKEN` (и `TELEGRAM_BOT_USERNAME` для ссылки). Без них весь интерфейс Telegram скрыт, сервер не падает. Получение сообщений — **long polling** (`getUpdates`) в процессе сервера, без вебхука: так проще на Render и локально. Для HTTP-запросов использовать встроенный `fetch` Node 20, без библиотек ботов.

**Привязка аккаунта.**
1. Пользователь в `/settings` → «Профиль» нажимает «Подключить Telegram».
2. Сервер создаёт код (6 символов, действует 15 минут) и возвращает ссылку `https://t.me/<bot>?start=<код>`.
3. Пользователь открывает ссылку и жмёт «Start». Бот получает `/start <код>`, находит код, сохраняет `telegram_chat_id`, удаляет код и отвечает «Готово, <имя>! Буду присылать уведомления Creative Desk».
4. В профиле — статус «Подключено» и кнопка «Отключить» (обнуляет `telegram_chat_id`).

**Поведение.**
- Каждое уведомление из F12 дублируется в Telegram тем, у кого подключён бот. Текст + кнопка-ссылка «Открыть» (на `PUBLIC_URL` из переменной окружения + путь к задаче).
- Для `task_submitted` дополнительно inline-кнопка **«✅ Принять»**. Нажатие → бот вызывает ту же доменную функцию приёмки, что и `POST /api/tasks/:id/accept` (вынести логику обработчика в функцию, чтобы не дублировать), с проверкой `allowedActions` от имени пользователя с этим `chat_id`. Результат — редактирование сообщения: «Принято ✅» или причина отказа («Задача уже не на проверке»).
- Правки из Telegram **не делаются** (нужен комментарий и пины) — для них кнопка «Открыть».
- Команда `/my` — список моих активных задач (для креативщика) или задач на проверке (для байера), до 10 строк.
- Ошибки Telegram API логируются и не ломают основное действие.

**API.**
```
POST /api/telegram/link     → { url, expires_at }
POST /api/telegram/unlink
```

**Критерии приёмки.**
- [ ] Без `TELEGRAM_BOT_TOKEN` сервер стартует, кнопки Telegram не видны.
- [ ] Кнопка «Принять» в Telegram переводит задачу в `done`, пишет историю от имени байера и создаёт уведомление креативщику.
- [ ] Повторное нажатие «Принять» по уже принятой задаче отвечает понятным отказом.
- [ ] Просроченный код привязки не срабатывает.

## 7. Нефункциональные требования

- **Производительность:** Библиотека с 2 000 креативов открывается < 1 с (пагинация по 60, индексы из раздела 2, агрегаты метрик одним `GROUP BY`, а не запросом на каждую карточку). Превью видео — `preload="metadata"`.
- **Адаптивность:** все новые страницы работают на ширине 375 px; таймлайн и тепловая карта на мобильном прокручиваются горизонтально внутри своего блока, а не всей страницей.
- **Доступность:** у всех иконок-кнопок есть `aria-label`/`title`; цвет статуса всегда дублируется текстом.

### 9.1. «Моя очередь» → короткий дашборд (меняет F5)

**Почему.** Прежняя очередь показывала 6 блоков у байера и руководителя: выгорающие, «внесите результаты», «ждут вердикта», «победители недели», «KPI недели», перегруз и простой. Экран не помещался, важное терялось среди второстепенного.

**Что теперь.** Ровно 3 блока на роль. Ключи в `GET /api/queue`: `summary` / `my_tasks` / `to_review` / `load` / `problems` / `available`.

| Роль | Блок 1 | Блок 2 | Блок 3 |
|---|---|---|---|
| Байер | Сводка: в работе · ждут проверки · в тесте · победителей за 7 дней · средний ROI за 30 дней. Плитки-предупреждения «Выгорают», «Ждут вердикта», «Без результатов» — только если число > 0 | Мои задачи в работе: статус, исполнитель, полоса оставшегося времени, по дедлайну | Ждут проверки: сколько ждёт (красным > 24 ч), «Открыть», «Принять» |
| Руководитель | Сводка за 7 дней со стрелкой к прошлой неделе: создано, сдано, % в срок, % с правками, победители, расходы на AI | Нагрузка: units / мощность (зелёный < 70 %, жёлтый 70–100 %, красный > 100 %), задач / WIP-лимит, план месяца | Проблемы — один список с меткой типа: «Просрочена», «Срочная без исполнителя», «Зависла на проверке», «Перегруз», «Выгорает»; сначала самые срочные |

### 9.2. План и норма креативщиков (новая функция)

**Почему.** Руководителю нужен понятный ориентир объёма на месяц, а креативщику — видеть, успевает ли он.

- **Данные.** Таблица `creative_plans (user_id, month 'YYYY-MM', norm > 0, UNIQUE(user_id, month))`. Норма по умолчанию хранится в `users.monthly_norm`, она действует, если на месяц нет своей записи.
- **Отступление от исходной постановки.** Добавлена колонка `users.monthly_norm_from` — месяц, с которого действует норма по умолчанию. Без неё норма, заданная сегодня, «появлялась» бы во всех прошлых месяцах. При смене нормы по умолчанию старое значение фиксируется записями в прошлых месяцах, где оно действовало, поэтому история план/факт не переписывается. Норму на прошлый месяц через API менять нельзя (400).
- **Факт** — креативы автора, принятые (`accepted_at`) в календарном месяце по Москве (UTC+3), без перекрытых версий.
- **Темп.** Ожидаемо к сегодняшнему дню = норма × прошедшие дни / дней в месяце; текущий день считается прошедшим. «Опережает» — факт ≥ ожидаемого, «в графике» — ≥ 85 % ожидаемого, «отстаёт» — меньше. Это чистые функции в `server/plan-math.js`.
- **API.** `GET /api/plans?month=` (lead — все, creative — свой, buyer — 403), `PUT /api/plans/:userId/:month {norm}` (lead; `norm: null` убирает норму на месяц), `GET /api/plans/report?from=&to=` для аналитики. Обычная норма задаётся через `PATCH /api/users/:id {monthly_norm}`. Изменения пишутся в историю как `plan_changed`; байер их в ленте не видит.
- **Интерфейс.** «Настройки → Команда»: колонки «Норма в месяц» и нормы на текущий и следующий месяц. Дашборд руководителя: «План: 24 / 40 (60 %)» цветом темпа. Дашборд креативщика: плитка «План месяца» с подписью «отстаёте на 3» или «в графике». Аналитика: таблица «План / факт» за выбранные месяцы.

### 9.3. Пометки на креативе (F7) — реализовано по спецификации, с уточнениями

- **Какие пины относятся к текущему раунду.** Текущие пины — на актуальных версиях креативов задачи: последняя версия слота, ещё не принята. Если креативщик сдал новую версию только одного креатива, открытые замечания на остальных остаются в силе. Пины заменённой версии в текущий раунд не входят: они показываются на новой версии полупрозрачными с пометкой «к прошлой версии». Отсюда правило «На правки»: комментарий необязателен, если есть хотя бы один открытый текущий пин.
- `round` пина = версия креатива, то есть раунд сдачи, в которой эта версия появилась.
- «Исправлено» ставит исполнитель задачи (и руководитель), вернуть в `open` может байер-владелец или руководитель. Удалять и править текст может только автор и только пока задача на проверке.
- **Сопутствующее исправление.** Файлы теперь отдаются через `res.sendFile` с поддержкой Range (206). Без этого браузер не перематывал mp4, и засечки на видео не работали. Заголовки безопасности (`nosniff`, CSP `sandbox`) сохранены.
